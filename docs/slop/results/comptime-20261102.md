# Compile-time decoders: what they link and what they cost per call, 2026-11-02

The measurements behind `docs/slop/comptime.md`. Intel(R) Xeon(R) Processor
@ 2.60GHz (Ice Lake-SP, family 6 model 106, 4 vCPUs, AVX-512), in an orb.
Zig 0.16.0, x86_64-linux. The prototype is `src/specialized.zig`
(`DecoderFor`, `EncoderFor`), and the experiment without a new type is
`src/inline_init.zig`. Programs and arms are in `bench/comptime/`.

## 1. What a program links

`bench/comptime/sizes.sh` builds one program per variant (`size.zig`). Each
program reads stdin, converts it with one variant of the API, and writes
stdout. Sizes are from `size -A`, net of `none`, which only copies stdin to
stdout. The `_label` variants also link the label table, which `label`
measures alone: 8,545 B of .rodata and 300 B of .text.

Findings:

1. **One encoding links one encoding.** windows-1252 decode drops from
   178,212 B of .rodata and 34,047 B of .text to 320 B and 812 B. That is its
   256-byte table, and the family's decoder with no dispatch. The windows-1252
   encoder is 480 B and 1,883 B, its table and the vector search.
2. **The CJK decoders link only their own tables:** Shift_JIS 29,650 B,
   gb18030 48,762 B, and EUC-KR 47,570 B, against 185 KB for all of them.
   Shift_JIS also links EUC-JP's and ISO-2022-JP's decoders and jis0212,
   because `japanese.zig` chooses among its three encodings at run time.
   §2 removes that.
3. **Sniffing costs UTF-8 and UTF-16.** `.sniff` can switch to either, so
   its decoders come along: 2,303 B more .rodata and 13,972 B more .text
   than `ct_1252`. This is why a set without `bom_encodings` takes
   `OptionsWithoutSniff`.
4. **Sets.**
   - `{UTF-8, windows-1252}`, net of the label table: 865 B of .rodata and
     6,294 B of .text.
   - Everything but CJK: 8,449 B and 15,571 B, mostly UTF-8 and UTF-16,
     against 176,489 B and 33,509 B for every encoding.
5. **The runtime type built from the generic links what the runtime type
   does.** `DecoderFor(&implemented)` is 608 B smaller in .rodata and 611 B
   smaller in .text than `Decoder`. I did not trace the difference.
   `Decoder.init` formats its panic message with `std.debug.panic`, where
   the prototype uses `@panic`, which is a likely part of it.
6. **Two types over one family share its code.** `both` adds a
   windows-1252 `DecoderFor` to a program with the full decoder. It costs
   109 B of .text and no .rodata, against `ct_1252`'s 812 B alone. The
   family's `decode` is one instance for both types, and only the wrapper is
   new.
7. **No new type** (`inline_init`): windows-1252 known at compile time
   links 296 B and 1,687 B. With the encoding chosen at run time, it costs
   19,260 B more .text than `Decoder`. Its symbols show the per-family thunks
   inlining some families' decoders, utf16's 8 KB among them, while
   out-of-line copies remain (4 instances of Japanese's `decodeSteps`
   against 2).

## 2. Japanese with `decodeAs` and `encodeAs`

The change asked of `src/japanese.zig` (in the report) splits `decode` and
`encode` into a run-time switch over `kind` that calls `decodeAs` and
`encodeAs`, which take the encoding at compile time. With it applied
locally to main, ReleaseSmall, net of `none`:

```
               before            after
ct_sjis        29,650 / 8,543    16,530 / 3,487    (.rodata / .text)
ct_enc_sjis    37,024 / 5,455    36,800 / 2,575
rt_label       185,642 / 34,420  185,642 / 34,420
rt_enc_label   192,608 / 13,792  192,608 / 13,792
```

Raw sizes after (`size -A`, before subtracting `none`):

```
none           rodata    18689 text    92133
ct_sjis        rodata    35219 text    95620
ct_enc_sjis    rodata    55489 text    94708
rt_label       rodata   204331 text   126553
rt_enc_label   rodata   211297 text   105925
```

Shift_JIS decode drops 13,120 B of .rodata, mostly jis0212's decode table
(13,026 B in `src/tables/jis0212.zig`), and 5,056 B of .text, EUC-JP's
and ISO-2022-JP's decoders. The runtime types
are the same size. Their speed with the change was not measured.

## 3. Per-call cost and throughput

`just arms="rust zig comptime generic inline" bench-compare 10` on
`wave1-core` at `2644ec3`, with the prototype's files copied in, 20 ms
samples (`BENCHTIME_MS=20`). The rows are all 8 shapes at 16 bytes, and
`web` and `nonascii` at 64 KiB. Twelve encodings cover every family:
windows-1252, KOI8-R, Shift_JIS, EUC-JP, ISO-2022-JP, GBK, gb18030, Big5,
EUC-KR, UTF-8, UTF-16LE, and x-user-defined. That is 460 rows, in all four
operations. Each arm is a `bench-<arm> serve` process pinned to core 3
(`taskset -c 3`). Every arm times each row back to back, in an order that
rotates from row to row and round to round, for 10 rounds after a sizing
round; then benchstat. The arms:

- `zig`: `bench/zig/arm.zig`, the runtime `Decoder` and `Encoder` as
  `wave1-core` has them.
- `comptime`: `bench/comptime/arm.zig`, each row calling a function
  specialized to its encoding: `DecoderFor(&.{e})` and `EncoderFor(&.{e})`.
  This is a program that knows its encoding at compile time.
- `generic`: `DecoderFor(&implemented)` and `EncoderFor(&implemented)`, the
  encoding chosen at run time. These are the runtime types built from the
  generic.
- `inline`: `inline_init.Decoder` with the encoding known at compile time;
  decode only.

All arms match encoding_rs's checksums on every row they have: 7,040 rows
(`inline` 3,608).

Geomean ns per call at 16 bytes, and GB/s at 64 KiB, over the rows both
arms have:

| rows           | zig       | comptime           | generic           | inline            | encoding_rs       |
| -------------- | --------- | ------------------ | ----------------- | ----------------- | ----------------- |
| decode, 16 B   | 19.31 ns  | 16.44 ns (0.851×)  | 18.94 ns (0.981×) | 16.02 ns (0.830×) | 22.88 ns (1.185×) |
| encode, 16 B   | 20.33 ns  | 18.37 ns (0.904×)  | 20.95 ns (1.030×) | -                 | 44.52 ns (2.190×) |
| all, 16 B      | 19.79 ns  | 17.33 ns (0.876×)  | 19.87 ns (1.004×) | -                 | 31.46 ns (1.589×) |

| encode, 64 KiB | 0.56 GB/s | 0.57 (0.985×)      | 0.56 (0.986×)     | -                 | 0.07 (7.958×)     |

Findings:

1. **One encoding is 12% faster per call at 16 bytes** (geomean, 368
   rows), and no different at 64 KiB. Single-byte and CJK decode take 7–9
   ns against 10–12 ns: windows-1252 to UTF-8 in 8.5 ns against 11.5, and
   Big5 in 7.1 against 9.6. The wrapper has no tag to test, the state is the
   family's own, and its fresh value is a constant.
2. **Japanese is the exception.** EUC-JP decode is 1.3 ns slower: 13.1
   against 11.8 ns to UTF-8. The family still switches on `kind` inside
   `decode`, and the whole `decode` is inlined into the caller. With
   `decodeAs` (§2) the specialized type would call one decoder directly.
   Not measured.
3. **The runtime types built from the generic cost the same:** 1.004×
   at 16 bytes and 0.989× at 64 KiB. Its init and dispatch compile to the
   same instructions as `Decoder`'s (1,109 against 1,098 lines in the
   caller).
4. **The inline-`init` experiment is fastest on decode at 16 bytes**
   (0.830×), faster than `comptime` on UTF-8: 11.4 against 16.6 ns. It calls
   the family out of line, through a pointer, so the caller stays small,
   while `comptime` and `zig` inline the family's whole decoder into the
   caller and pay its prologue. That is a hint for the specialized wrapper:
   keeping some families out of line (as `japanese.zig` already does with
   `@call(.never_inline)`) may beat inlining them. The core orb measured
   the opposite for some encoders, so it is per family. Not pursued here.

Two mistakes found on the way, both fixed before the run above:

- **One call site, or 41.** The first run built the `generic` arm with one
  function per encoding, so its decoder had 41 call sites and LLVM kept
  `decodeToUtf8` out of line. It was 1.34× `zig` (26.24 against 19.56 ns
  geomean at 16 bytes). With one function, as `bench-zig` has, the decoder
  is inlined. A real program that calls `Decoder` from several places sees
  the out-of-line cost, which `bench-zig` does not measure.
- **A runtime popcount in `init`.** `if (set.count() == 1)` in `fresh` ran
  at run time. Zig does not evaluate a call at compile time just because
  its arguments are known, so every `init` popcounted the set's bits loaded
  from .rodata and copied the state twice. That cost the `generic` arm 7%
  (1.071×). `comptime set.count()` fixed it.
