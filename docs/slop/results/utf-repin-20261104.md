# utf v0.2.0 repin, 2026-11-04

Wave 6. The owner chose that utf owns every UTF kernel and the run-time
dispatch, so a binary has one dispatcher. utf v0.2.0 adds
`utf.convert.bmpToUtf8` and `utf.convert.utf8ToBmp`, wave 5's converters
moved into utf under its `dispatch.call` (utf's
bmp-converters-20261104.md). This branch pins v0.2.0, switches the
single-byte and x-user-defined staging to them, deletes encoding's copies,
adds a `-Ddispatch` build option that reaches utf, and re-measures speed
and size against main (wave 5) and the README's CPU table.

Headlines (the machine and method follow):

1. **Speed without dispatch is wave 5's.** utf's converters against
   encoding's at the same level: decode to UTF-8 1.02x on x86-64-v3, 0.99x
   on -v2, 1.00x at baseline; encode from UTF-8 1.02x, 0.97x and 0.98x.
   The slowest like-for-like cells are -v2's encode from UTF-8 from 256
   bytes up and decode at 16 and 64 bytes, 0.96-0.97x.
2. **With dispatch (utf's default for a generic x86-64 build), the
   baseline gets its speed back on a newer CPU.** On this AVX-512 CPU a
   baseline build decodes single-byte text to UTF-8 at 1.49x main
   (1.8-1.9x from 256 bytes) and encodes from UTF-8 at 1.26x; against the
   build before wave 5, 0.96x and 0.99x. Its decode rows below encoding_rs
   go from 264 (main) to 47. Those 47, Latin text with the odd accented
   letter, are slow in the block lookup, not the converter: DecodeUtf16,
   which converts nothing, is 0.69x the pre-wave-5 build on them
   (decision 2). -v3 and -v2 builds with dispatch: 1.12-1.17x main.
3. **Size: dispatch costs the small programs 34 to 56 KB.** A one-encoding
   windows-1252 decoder is 47 KB for x86-64-v3, 59 KB for -v2 and 62 KB
   for baseline with dispatch (main 13, 14 and 6 KB), and 13, 14 and 6.5
   KB without; `Decoder` is 2 to 22 KB larger than main with dispatch and
   43 to 110 KB smaller without. The host and aarch64 are within 1 KB of
   main, or smaller. utf's tier objects keep their constants whole, which
   the queued utf v0.2.1 addresses (decision 1).
4. **CJK, UTF-8 and UTF-16 are unchanged.** The CJK decoders and encoders,
   and `utf16.Decoder.decode`, are the same machine code as main's; their
   only moves (host Japanese and UTF-16 decode to UTF-16, 0.89-0.93x) are
   placement. Everything that calls utf for UTF-8 and UTF-16 is within 3%.
5. **The README's CPU table**, re-measured with its 10-round method: at
   64 KiB, single-byte decode 7.60x encoding_rs on the host, 5.51x for
   x86-64-v3 and 3.24x for baseline; encode 7.11x, 5.49x and 3.99x; every
   row 6.69x, 5.39x and 3.81x (section 5, proposed text in the report).
6. Gates: `just ci` (re-run after a lint fix), `just oracle 20000`, `just
fuzz 600`, and a fuzz of the 31 single-byte encodings and x-user-defined
   on `-Dcpu=x86_64_v3` and `-Dcpu=x86_64` builds, each with and without
   dispatch, all exit 0; `rg setRuntimeSafety src` empty (section 7).

## Machine

Intel(R) Xeon(R) Processor @ 2.60GHz (family 6 model 106, Ice Lake
server), 4 vCPUs (CPUs 0 and 1, 2 and 3 are hyperthread siblings) in a
KVM orb, AVX-512 with BW, VL, VBMI and VBMI2, Linux 6.1. Zig 0.16.0,
ReleaseFast for speed and ReleaseSmall for sizes; encoding_rs 0.8.44
(`rust`) for Rust's default x86-64 target (SSE2), as the harness builds
it. A shared host: read ratios, not absolute GB/s. Every build runs on
this one CPU, so a dispatching x86-64-v3, -v2 or baseline build runs
utf's AVX-512 kernels here, and only the builds without dispatch show what
an older CPU of that level runs. aarch64 speed is not measured (`just
test-aarch64` runs its paths under qemu), only its sizes.

## 1. Change

Three commits on origin/main `25a5a25`:

- `build: repin utf to v0.2.0 and pass its dispatch option through`:
  `build.zig.zon` pins utf v0.2.0. `build.zig` declares `-Ddispatch` and
  hands it to the utf dependency; unset, it passes nothing, so utf's
  default holds (on for a generic x86-64 CPU, off for a native or named
  one). A consumer sets it with `b.dependency("encoding", .{ .dispatch =
false })`. `bench/build.zig` and `bench/comptime/build.zig` forward it
  for the measurements.
- `codec: stage single-byte text through utf's BMP converters`:
  `single_byte.zig` and `x_user_defined.zig` call `utf.convert.bmpToUtf8`,
  and `codec.encodeStaged` calls `utf.convert.utf8ToBmp`. `codec.zig` loses
  `bmpToUtf8`, `utf8ToBmp`, the `Pack` choice, the three shuffle tables,
  the intrinsics, `Converted` (callers use `utf.BmpResult`), and the two
  converter tests (they moved to utf with the code): about 550 lines.
  `encodeStaged` passes all of its input to `utf8ToBmp`, which stops where
  the stage is full and no longer stops near the end of the input, and
  `staged_min` is 64 bytes on every target (it was 66 on the AVX-512 host,
  the window plus two).
- The results file.

Unchanged: the single-byte block lookup (`pshufb`, `tbl`, `vpermi2w`, the
baseline gather), the call sites' character-at-a-time paths, and every
CJK family (they call neither the staging nor utf).

  v0.1.0 already dispatched UTF-8 and UTF-16, and each tier now carries
  the BMP converters too.
- **The host and aarch64** are level: they have no dispatch, and utf's
  converters are ours.

The CJK decoders and encoders run no changed code: their ReleaseSmall
programs are byte for byte the same (section 2), and in the host's two
benchmark binaries every Big5, gb18030, Japanese and EUC-KR function is the
same machine code, instruction for instruction once addresses are masked
(a scratch comparison of `objdump -d` per function). The host's DecodeUtf16

byte loops.

0.95 to 1.08.

## 6. Decisions for the owner

1. **utf's default dispatch, and its size: already queued.** As asked,
   `-Ddispatch` defaults to utf's choice, on for a generic x86-64 target.
   That gives a baseline build on a newer CPU its speed back (section 3),
   but a one-encoding single-byte decoder or encoder for a generic x86-64
   target is 45 to 62 KB instead of 6 to 14 KB, and `Decoder` 2 to 22 KB
   larger than main. The owner has queued utf v0.2.1 to shrink dispatch
   (plan.md: split the AVX-512 tier's `.rodata`, up to 26 KB, and share the
   BMP shuffle tables between the SSE and AVX2 tiers, 12.8 KB); these
   numbers are its baseline. What would remain is about the tiers' code and
   the dispatcher (3.7 KB of `.text` on -v3). Meanwhile `-Ddispatch=false`
   is there for size-sensitive generic builds, and the README should say
   so (proposed text in the report). No decision needed beyond the README
   text.
2. **Wave 5's baseline gather costs sparse Latin text (recommended: a small
   follow-up in `single_byte.zig`, not dropping it now).** With dispatch
   restoring the conversion, what is left of the baseline's loss against
   the pre-wave-5 build is the block lookup: DecodeUtf16 0.80-0.83x on
   `csv`, `mail`, `subtitles` and `web`, and 0.69x on the 47 rows where
   decoding to UTF-8 is still below encoding_rs, text whose blocks hold
   few bytes from 0x80 and take the lane-by-lane patch, not
   `gatherBlock`. The gather still
   brings `nonascii` from below encoding_rs to 1.27x the old lookup. A
   follow-up could find what the sparse path pays for (the `dense` test,
   the gather's code in the same loop, or placement alone) with the
   placement method;
   dropping the gather would put the pre-wave-5 build's 143 DecodeUtf16
   rows below encoding_rs back, nearly all `nonascii`.
3. **16-byte non-ASCII decode on -v2 with dispatch (recommended:
   accept).** `mixed` and `nonascii` at 16 bytes decode to UTF-8 at 0.82x
   main: a dispatched call costs more than 16 units of inline SSSE3 code.
   -v3 is 1.04x on the same rows, and from 64 bytes up -v2 is 1.04-1.28x.
   utf could convert a short input before its dispatch; not worth asking
   for on its own.
