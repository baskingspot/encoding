# Shift_JIS, EUC-JP, and ISO-2022-JP against encoding_rs, 2026-11-02

The wave 1 Japanese codecs (`src/japanese.zig`, tables in the
`japanese_paged` layout; see `japanese-tables-20261102.md` for why) against
encoding_rs 0.8.44 and the comparison arms, on every Japanese row of the
corpus.

Headline: 2.98× encoding_rs geomean over 528 rows (zig
0.84 GB/s geomean). Decode is 1.04–2.00× encoding_rs per encoding and
direction; it trails on 16-byte calls (0.93× geomean at 16 B, against
2.3–2.4× at 1 MiB). Encode is 5.1–7.3×, from encoding_rs's linear kanji
search in its default build. Our Japanese tables take 50,005 B of `.rodata`
against encoding_rs's 26,262 B.

## Method

Intel(R) Xeon(R) Processor @ 2.60GHz (4 vCPUs, AVX-512), in an orb. Zig
0.16 ReleaseFast for the host CPU; encoding_rs 0.8.44 (default features),
ICU 78.3, glibc iconv, GNU libiconv, Go x/text v0.43.0. `BENCHTIME_MS=20
just bench-compare 10 'Shift_JIS|EUC-JP|ISO-2022-JP'`: each arm is a server
pinned to one core, all arms time each row back to back in rotating order,
10 rounds, medians. Go has no UTF-16 rows.

## How the codecs are built

- **Decode.** Shift_JIS and EUC-JP run a loop that copies ASCII 16 bytes at
  a time with `@Vector` while the output has room for the block, then
  decodes a lead/trail pair straight from the index (`sjisPair`,
  `eucPair`, returning a plain `u21` with 0 for "not a pair"). Everything
  else (errors, EUC-JP's 0x8E and 0x8F sequences, a sequence cut by the end
  of the input) goes through a step function that is the standard's
  algorithm line by line; a cut sequence is held in two bytes of state.
  ISO-2022-JP runs the standard's state machine with fast paths for ASCII
  runs, two-byte runs in the jis0208 state, and whole escape sequences.
- **Encode.** One loop for Shift_JIS and EUC-JP: ASCII runs by SIMD, then a
  rank lookup in the jis0208 reverse table. Shift_JIS's pointer exclusion
  (8272..8835 maps to the first pointer in 10716..11103 instead) is a scan
  of that small range only when the found pointer falls in it. ISO-2022-JP
  tracks the ASCII, Roman, and jis0208 states and emits escapes on change.
- **Per-call cost.** The codec dispatches with `@call(.never_inline, ...)`
  per encoding kind so each kind's loop is one function; with the
  dispatcher inlined, 16-byte calls were slower.
- **Codegen.** In Zig 0.16 a `?u21` built with `if (x) null else y`, and a
  `u21` field of a struct returned by value, compile to a store and a
  reload that stalls on store forwarding. The codec's scalar reader returns
  a `u32` code point and its pair decoders return `u21` with 0 for none;
  fixing the two doubled to tripled throughput (Shift_JIS decode to UTF-8
  0.22 → 0.51 GB/s on flat tables, encode from UTF-8 0.144 → 0.397 GB/s).

## Against encoding_rs

Geomean GB/s and ratio to encoding_rs (above 1 means we are faster):

|                    | Shift_JIS        | EUC-JP           | ISO-2022-JP      |
| ------------------ | ---------------- | ---------------- | ---------------- |
| decode to UTF-8    | 0.75 GB/s, 1.04× | 0.92 GB/s, 1.46× | 0.66 GB/s, 1.87× |
| decode to UTF-16   | 0.91 GB/s, 1.27× | 1.12 GB/s, 1.28× | 0.79 GB/s, 2.00× |
| encode from UTF-8  | 0.77 GB/s, 5.14× | 0.89 GB/s, 5.73× | 0.57 GB/s, 6.22× |
| encode from UTF-16 | 0.97 GB/s, 5.87× | 1.14 GB/s, 6.75× | 0.77 GB/s, 7.30× |

Per call, the median row's time:

| ns per call        | 16 B             | 64 B         | 256 B      |
| ------------------ | ---------------- | ------------ | ---------- |
| decode to UTF-8    | 32.9 (rust 33.8) | 71.2 (121.5) | 364 (541)  |
| decode to UTF-16   | 31.1 (rust 30.1) | 56.3 (103.2) | 270 (437)  |
| encode from UTF-8  | 24.6 (rust 28.2) | 92.9 (694)   | 579 (5018) |
| encode from UTF-16 | 24.1 (rust 29.3) | 78.9 (694)   | 452 (4927) |

`bench-compare` counts 72 of the 528 rows slower than encoding_rs, all but
two of them decode, and most at 16 B to 4 KiB. The largest group is
Shift_JIS decode to UTF-8 on real text (web, mail, CSV, subtitles,
non-ASCII), which runs at 0.66–0.95× from 16 B to 4 KiB and 1.2–2.3× from
64 KiB up. ISO-2022-JP's `invalid` rows are the slowest, 0.51–0.56× up to
256 B and 0.75–0.81× above. Against the other arms we are
2.7× (Go) to 5.2× (glibc iconv) geomean.

Every arm's output was checked against the reference before timing: zig
matches on every row it runs (0 differ).

encoding_rs's Japanese tables in `bench-rust` (`nm -S`, default features):
26,262 B: `JIS0208_LEVEL1_KANJI` 5,930, `JIS0208_LEVEL2_AND_ADDITIONAL_KANJI`
6,780, `IBM_KANJI` 720, `JIS0208_SYMBOLS` 480 and the range and symbol
triples 174, `JIS0212_KANJI` 11,602, `JIS0212_ACCENTED` 510 and its triples
66; kana and katakana are arithmetic, and there is no reverse table, so
kanji encode searches the kanji arrays linearly. Its
`less-slow-kanji-encode` feature adds a sorted table of the 2,965 level 1
kanji with their bytes (11,860 B) and `fast-kanji-encode` a direct table of
bytes for U+4E00 to U+9FA0 (41,794 B, 68,056 B in total, more than ours).

`just bench-rodata` counts only the single-byte tables so far (6,912 B in
each binary); the whole `.rodata` is 167,245 B for `bench-zig` (no Chinese
or Korean tables yet) and 186,652 B for `bench-rust`.
