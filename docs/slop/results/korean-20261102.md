# EUC-KR against encoding_rs, and its table layout, 2026-11-02

The wave 1b Korean codec (`src/euc_kr.zig`, index EUC-KR in
`src/tables/euc_kr.zig`) against encoding_rs 0.8.44 and the comparison
arms on every EUC-KR row of the corpus. It also covers plan decision 1 for
index EUC-KR, `japanese_paged` against `chinese_rank`'s flat decode, and the
decode loop change that the comparison turned up.

Headline: decode is 1.23x encoding_rs geomean to UTF-8 and 1.28x to
UTF-16 over 44 rows each (1.08 and 1.15 GB/s), and encode 3.52x from UTF-8
and 4.72x from UTF-16 (0.91 and 1.53 GB/s), because encoding_rs encodes by
searching its decode tables. Korean text to UTF-8 is level with encoding_rs
(0.99x at 64 KiB, 1.04x at 1 MiB). Calls on 16 bytes cost 17.4 ns against
12.6 to decode (0.72x) and 14.0 against 11.6 to encode (0.85x); the decode
gap is the same on windows-1252, so it is in the shared decoder path. The
table is `chinese_rank` (flat decode, rank encode): 89,094 bytes against
encoding_rs's 21,770, and 6,334 bytes more than `japanese_paged`, which
decodes 5% slower.

## How the codec is built

- **Decode.** As Big5's: ASCII 16 bytes at a time with `@Vector`
  (`gb18030.asciiRun`) while the input and output have a block left. A lead
  byte from 0x81 to 0xFE with a trail from 0x41 to 0xFE that the index maps
  is decoded in the loop. Everything else goes to an out-of-line step that
  is the standard's algorithm: 0x80 and 0xFF are errors, an ASCII trail
  byte is restored (read again), and a lead byte at the end of a call's
  input is held in the decoder. Index EUC-KR has no code point below U+00A1
  or above U+FFFF, so the loop writes one UTF-16 unit, or two or three UTF-8
  bytes, without the general writer's range checks.
- **Encode.** ASCII runs by SIMD, then the rank lookup into index pointers;
  lead `pointer / 190 + 0x81`, trail `pointer % 190 + 0x41`. Index EUC-KR
  has no code point twice, so every decoded character encodes back to its
  own bytes (a unit test checks all 23,940 lead and trail pairs).
- **Codegen.** Two optionals cost the decode loop a trip through memory on
  every character, as the wave 1 lesson about `?u21` warns:
  - `codec.tryPut` returns `?usize`. Inlined into the loop, its `orelse`
    compiled to a select between the address of a constant null and a stack
    slot, then a load. The loop's own writer returns 0 when the character
    does not fit.
  - The table's `decode(pointer) ?u21`, captured with `if (...) |cp|`,
    stores the code point to a stack slot as a word and a byte and loads it
    back. Unwrapping it at once (`orelse 0` into a `u32`) drops the load;
    the stores stay, because the generated `decode` returns an optional.
    A `decode` that returned a plain `u32`, 0 for none, removes them too
    (the `raw` arm below, built with such a function added to the
    generated table for the measurement only): another 2% geomean on
    decode, and 14% to 15% on Korean text. That is a change to the
    generated layouts, which the core orb owns, so it is a request in the
    report, not in this branch.

## Decision 1 on index EUC-KR: flat decode

Index EUC-KR has 17,048 code points over pointers 0 to 23,749 (rows of 190).
Leads 0x81 to 0xC6 fill 178 of each row (UHC's extension Hangul), and leads
0xC7 to 0xFD only the 94 trails from 0xA1; lead 0xC9 and 0xFE have none.
The empty runs are what pages share.

| layout           | decode | encode |  total |
| ---------------- | -----: | -----: | -----: |
| `japanese_paged` | 41,166 | 41,594 | 82,760 |
| `chinese_rank`   | 47,500 | 41,594 | 89,094 |

`japanese_paged` picks pages of 32 (743 u16 page numbers and 620 pages
of u16 code points); `chinese_rank` is one u16 per pointer. Both encode
with the same rank table. `.rodata` of `bench-zig`: 438,717 bytes with
`japanese_paged`, 445,021 with `chinese_rank`, 6,304 apart.

Speed, the same codec on both tables (`zig` is `chinese_rank`, `paged4`
`japanese_paged`), geomean GB/s over the 44 rows of each operation and
the ratio to encoding_rs:

| op                 | rows | rust GB/s (×rust) | zig GB/s (×rust) | paged4 GB/s (×rust) |
| ------------------ | ---: | ----------------: | ---------------: | ------------------: |
| DecodeUtf16/EUC-KR |   44 |      0.937 (1.00) |     1.198 (1.28) |        1.131 (1.21) |
| DecodeUtf8/EUC-KR  |   44 |      0.922 (1.00) |     1.126 (1.22) |        1.072 (1.16) |
| EncodeUtf16/EUC-KR |   44 |      0.338 (1.00) |     1.603 (4.74) |        1.604 (4.74) |
| EncodeUtf8/EUC-KR  |   44 |      0.268 (1.00) |     0.948 (3.53) |        0.942 (3.51) |

Encode ties, as it should with the same table. Decode with pages is 5%
slower geomean on both outputs (benchstat over the 88 decode rows:
-5.19%), and 7% to 11% slower on Korean text (`nonascii`, all Hangul and
Hanja): 740 against 797 MB/s to UTF-8, 868 against 972 to UTF-16. The
page number is one more load on every character's dependency chain. Per-call
cost at 16 bytes is the same on both (16.8 and 17.0 ns to UTF-8).

**Choice: `chinese_rank`.** Flat decode costs 6,334 bytes (7.7% of the
Korean tables, 1.4% of the binary's `.rodata`) and buys 5% on every decode
row and up to 11% on Korean text. It is also what decides Korean text to
UTF-8 against encoding_rs: 797 MB/s against 812 (0.98x) on the flat table,
740 (0.91x) paged. Both layouts are about 4x encoding_rs's 21,770 bytes, so
the bytes do not decide the memory bar either way. This amends the plan's
verdict, which listed euc_kr with the paged indexes: pages save bytes on
index EUC-KR, but less than on jis0208 (29%), and the decode cost is the
same as on the dense Chinese indexes. Switching back is one word in
`gen/sources.zig` and `just gen`.

Before the codegen fix the gap was wider and different in kind: the old
loop (`tryPut`, captured `?u21`) on the paged table decoded to UTF-16 at
1.05x encoding_rs and on the flat table at 1.22x, so an earlier run of
the original codec showed pages 13% slower to UTF-16. With the fix both
tables gain, paged more (1.05x to 1.21x).

## Tables against encoding_rs

encoding_rs 0.8.44's Korean tables, by `nm --size-sort` of the Rust bench
binary (default features, no `fast-hangul-encode` or `fast-hanja-encode`):
`KSX1001_HANJA` 9,776, `KSX1001_HANGUL` 4,700, `CP949_TOP_HANGUL_POINTERS`
and `_OFFSETS` 2,158 each, `CP949_LEFT_HANGUL_POINTERS` and `_OFFSETS`
1,070 each, `KSX1001_SYMBOLS` 330, `KSX1001_OTHER_POINTERS` 156,
`KSX1001_OTHER_UNSORTED_OFFSETS` 154, `KSX1001_BOX` 136,
`KSX1001_LOWERCASE` 32, `KSX1001_UPPERCASE` 30: 21,770 bytes, which serve
both directions. Its decoder maps the UHC extension through those range
tables, and its encoder searches the decode tables, which is where the
4–9x encode difference comes from. Ours: 89,094 bytes, 47,500 to decode and 41,594 to encode. A decoder-only
build that searched the decode table to encode would be 47,500 (the
`chinese_scan` trade in chinese-layouts-20261102.md).

`just bench-rodata`: `.rodata` of `bench-zig` 445,021 bytes against
355,869 on `origin/main` (`16d1fa2`), so EUC-KR adds 89,152 bytes, the
table's 89,094 and 58 of other constants; `.text` grows by 5,792 bytes.
`bench-rust`'s `.rodata` is 186,652 bytes for every encoding_rs encoding.

## Differences from encoding_rs

None found. `just oracle 20000` compares EUC-KR with encoding_rs on 20,000
random inputs, every byte at both sides of the SIMD blocks, every two-byte
sequence, and three- and four-byte sequences from the lead and trail
alphabet, to UTF-8 and UTF-16, in both modes, in one call and a byte at a
time, and the encoder on random text and every scalar value: 1,981,568
comparisons, 0 mismatches, nothing added to `known`. The
web-platform-tests Korean files (every index entry decoded and encoded
under ten labels, and the error cases) all pass.

## Method

Intel(R) Xeon(R) Processor @ 2.60GHz (4 vCPUs, AVX-512), in an orb. Zig
0.16 ReleaseFast for the host CPU; encoding_rs 0.8.44, ICU 78.3, glibc
iconv, GNU libiconv, Go x/text v0.43.0. Each arm is a server pinned to one
core (`taskset`); every arm times each row back to back in rotating order,
50 ms samples, 10 rounds, medians, benchstat against encoding_rs. The
layout and loop arms are `bench-zig` binaries built from this branch with
the `.layout` of index EUC-KR or `src/euc_kr.zig` changed and copied to
`zig-out/bin/bench-<name>`, run with `just arms="rust zig paged4 rank3
paged3 rank paged raw" bench-compare 10 EUC-KR`; every arm's output matched
encoding_rs on all 6,688 rows it checked. Table bytes are counted from the
generated arrays.
