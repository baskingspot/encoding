# GBK, gb18030, and Big5 codec loops, 2026-11-02

The first GBK, gb18030, and Big5 codecs (`33217e1`) ran every non-ASCII
byte through the standard's whole step function, inlined into the loop with
the held-bytes logic, the four-byte ranges, and the error paths, and copied
ASCII in 16-byte blocks between 16-byte stretches of characters. The loops
now:

- take a two-byte sequence (and, in the encoders, a code point in the
  index) on an inline fast path, and send everything else (errors, the
  four-byte ranges, Big5's two-code-point pointers, the bytes held across
  calls, GBK's U+20AC, the Private Use table, U+E5E5, numeric character
  references) to an out-of-line function, so the hot loop keeps `src`,
  `dst`, and its offsets in registers;
- copy ASCII in a tight 16-byte loop that starts when an ASCII byte (or
  unit) appears and stops at the first non-ASCII one;
- read the three-byte UTF-8 of CJK text inline in the encoders, and carry
  the code point as a `u32`. A `u21` merged from two paths (the inline read
  and `codec.readScalar`'s result) is lowered as a three-byte store and a
  four-byte load through the stack: a store-forwarding stall on every
  character. With the `u21`, gb18030 encode from UTF-16 ran at 100 MB/s on
  pure Chinese; with the `u32`, 580 MB/s.

Headline: +38.1% geomean over all 528 GBK, gb18030, and Big5 rows (decode
to UTF-8 +52%, to UTF-16 +64%, encode from UTF-8 +36%, from UTF-16 +7.5%);
424 rows faster, 25 slower, 79 within noise. These numbers are on the
committed `flat` tables, whose `decode` has the same kind of stall (its
`?u21`; see `chinese-layouts-20261102.md`), so decode is still 0.66–0.86x
encoding_rs here. The layout study measures it on the other tables.

## Method

Intel(R) Xeon(R) Processor @ 2.60GHz (4 vCPUs, AVX-512), in an orb. Zig
0.16 ReleaseFast for the host CPU. `just arms="rust zig old" bench-compare
5 'GBK|gb18030|Big5'`: `old` is the arm built at `33217e1`, `zig` after the
change, both on the committed flat tables; encoding_rs 0.8.44 the
reference. Each arm is a server pinned to one core (`taskset`), and the
three time each row back to back in rotating order, 5 rounds of 50 ms
samples. Then `benchstat old.txt zig.txt` (n=5, so benchstat gives p-values
but no intervals).

The slower rows: ASCII-only inputs of 4096 bytes −6 to −8% (the old loop
copied a long ASCII run with `@memcpy` once its extent was known; the new
one copies 16 bytes at a time, still 19–20 GB/s, 2.3x encoding_rs), and
short invalid or mixed inputs to UTF-16 encode −6 to −17% (the out-of-line
call on each error or each non-ASCII character in a short buffer).
