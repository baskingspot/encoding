# Core and IBM: per-call cost, the encoder's reader, the shared helpers, table sizes, and IBM 437 and 850, 2026-11-02

Wave 1b, core. Intel(R) Xeon(R) Processor @ 2.60GHz (Ice Lake-SP, family
6 model 106, 4 vCPUs, AVX-512), in an orb. Zig 0.16 ReleaseFast for the
host CPU; encoding_rs 0.8.44. Every A/B below is interleaved and pinned:
each arm is a `bench-<arm> serve` process pinned to core 3 (`taskset -c
3`), and every arm times each row back to back, in an order that rotates
from row to row and round to round, 20 ms samples, 10 rounds after a
sizing round; then benchstat. `head` is the bench arm built at `16d1fa2`
(origin/main). Commit hashes name this branch's commits as rebased onto
`fd516e1`; each arm was built from the same change on an earlier base.

Headlines:

1. The 16-byte regression was a store-forwarding stall in
   `Decoder.init` and `Encoder.init`, not the dispatch. Copying the fresh
   state from a compile-time table took 16-byte calls from 22.8 to 16.7 ns
   geomean over 336 rows; windows-1252 `web-16` decode to UTF-16 went from
   16.4 to 8.6 ns.
2. The encoders' reader returns a `u32` and reads two-byte UTF-8 inline:
   +64% geomean over 192 encode rows; single-byte encode from UTF-8 is 2.6
   to 3.2 times faster.
3. The shared helpers moved to codec.zig with no change (+0.4% geomean).
4. Tables: 333,075 bytes against encoding_rs's 124,497 (2.68 times).
5. test-layouts keeps 3 layouts.
6. IBM437 and IBM850 agree with glibc, GNU libiconv, and Go's x/text on
   every row; ICU differs on 3 bytes by design.
7. The tables' `decode` returns a `u32`: +10.9% geomean over 98 CJK decode
   rows. A `tryPut` without an optional measured nothing and is not in.
8. Single-byte decode, and encode from UTF-16, of long Latin text swings
   by up to 40% with where the linker puts the loops, already on
   origin/main. Aligning the functions fixes it on native targets but
   cannot build for wasm; an owner decision.
9. The full `bench-compare` against `16d1fa2`: +32.5% geomean over 6,512
   rows, every family and operation at or ahead.

## 1. The 16-byte per-call cost

### Cause

Not the dispatch: every family's `decode` was already out of line, and
`single_byte.Decoder.decode` compiles to the same 215 instructions before
and after the Japanese family landed. The cost is in `Decoder.init`.
`codecs.initDecoder` builds the state union at run time, one branch per
family, each writing its payload and then the tag byte with narrow
stores (an 8-byte table pointer and a 1-byte tag for single_byte). LLVM
keeps it out of line and returns the union through memory, and the
inlined `Decoder.init` copies it into the decoder with one 16-byte
`vmovups` load: a load wider than the stores it reads, which cannot be
forwarded and waits for them to retire. Before the Japanese family, the
inlined copy in `decodeToUtf16`'s caller happened to go field by field
(no stall), while `decodeToUtf8`'s already used the vector copy, which is
why decode to UTF-8 sat about 6 ns behind encoding_rs on every family.
Adding Japanese grew the union and changed LLVM's choice for UTF-16 too.
`Encoder.init` had the same copy.

Forcing `initDecoder` inline does not help: the per-family branches
still merge their union through a stack slot and copy it with the wide
load (and `Decoder.init` then goes out of line and copies the whole
decoder the same way): 8% slower geomean over the rows below.

### Fix

`Decoder` and `Encoder` copy the fresh state from a table built at
compile time, one entry per implemented encoding (`fresh_states`). The
copy is a 16-byte load from read-only data and a 16-byte store, which
later narrow loads of the tag and payload forward from. The cost no
longer depends on how many families the union has or how LLVM inlines
their initializers: a new family adds a table entry, not a branch. The
tables are 41 entries of 16 bytes (decoders) and 24 bytes (encoders).

Geomean over the 336 rows: 22.77 → 16.71 ns per call (−26.6%), 0.818 →
1.115 GB/s (+36.3%). windows-1252 `web-16`, the Chinese orb's row:
decode to UTF-16 16.4 → 8.6 ns (it was 9.95 ns at `1d80964`, before the
Japanese family, in a 5-round A/B here; 11.6 in the Chinese orb's run),
and to UTF-8 16.7 → 9.6 ns. Decode at 16 bytes is now at or ahead of
encoding_rs on every family but UTF-16LE (19.1 against 16.9 ns to
UTF-16) and x-user-defined.

One family got slower: x-user-defined decode to UTF-8, 21.3 → 31.1 ns.
Its decoder is a byte loop that LLVM inlines into the dispatcher (the
only family besides replacement that it inlines), and the loop's
instructions are the same before and after; it moved. Called out of line
(`@call(.never_inline, ...)` in the dispatch, measured as an experiment)
it is 20.5 ns. With the dispatch out of line for every family, Shift_JIS
and UTF-8 encode lose 5–6 ns instead, so the dispatch stays as it is.

## 2. The encoders' reader: a `u32` code point, and two-byte UTF-8 inline

`codec.Scalar` keeps its `u21`: `utf8.zig` and `x_user_defined.zig`,
which this orb does not own, pass `Scalar.cp` where a `u21` is wanted
(`EncodeResult.unmappable`, `tryPut`), and the public `unmappable` field
stays a `u21`. The readers return a plain `u32` instead: `codec.read`
(section 3 moved it from gb18030.zig) returns `Read{ cp: u32, len: u32 }`,
and the single-byte encoder now uses it in place of `codec.readScalar`.

That alone speeds up encoding from UTF-16 (+6–39% per encoding) and not
from UTF-8: a two-byte UTF-8 character, the bulk of Latin, Greek,
Cyrillic, Hebrew, and Arabic text, still went through the out-of-line
`readScalar`. So `codec.read` reads well-formed two-byte sequences inline
too. Where that check goes matters: first, it costs the CJK encoders
2–6% on their three-byte characters; second, it costs the single-byte
encoders
4–15%. So the caller says which it sees most, `read(Unit, src,
i, first)` with `first` 2 or 3, a comptime parameter. On the UTF-8 encode
rows of 8 encodings (A/B of 2-byte first `u32b`, 3-byte first `u32c`, and
the caller's choice `u32d`, against `before`, `ed0f653`), geomean GB/s:

## 3. The shared helpers in codec.zig

A refactor: gb18030.zig's `asciiRun`, `asciiRunOut`, `highBits`, and its
`u32` reader (`Read`, now `codec.read`), and the copies of `copyAscii`,
`narrowAscii`, and `asciiUnits` in single_byte.zig and japanese.zig, are
one each in codec.zig; `asciiPrefixBlocks` takes the unit type and
replaces `asciiUnits`, and japanese.zig's `readScalar` (the same reader)
goes. Big5 no longer imports gb18030.zig.

The same machine code, mostly: `single_byte.Encoder.encode` for UTF-16
compiles to the same instructions before and after, its RIP-relative
offsets aside. But functions move, and on this machine that alone moves
some rows by 10–40%: the windows-1252 UTF-16 encoder, byte for byte the
same, is 0xE0 bytes further down and 18–43% slower on its non-ASCII rows,
while the Japanese UTF-16 encoders got 10–29% faster from a register
allocation change. Over the 256 rows (8 encodings, 4 operations, 8 shapes
from 16 bytes to 4 KiB; `before` is `d5d6dbe`, `after` this change), the
geomean is unchanged: +0.37%, 1.553 → 1.559 GB/s.

## 6. IBM437 and IBM850

Two tables in the single-byte family, generated from Unicode's mappings
of Microsoft's tables (`vendor/unicode/CP437.TXT`, `CP850.TXT`), which map
all 256 bytes, so their decoders never report an error. `test/tables.zig`
checks both in full against the vendor files, both directions, as it does
the standard's single-byte encodings against their indexes: every byte,
alone in fatal mode and all together, and every scalar value in html and
fatal mode; it also checks that the files map bytes 0x00 to 0x7F to
themselves, as the single-byte decoder assumes.

encoding_rs lacks them, so the oracle skips them (they have no label).
The cross-check is the benchmark arms' checksums over the 352 IBM437 and
IBM850 rows of the corpus (8 shapes, 16 bytes to 1 MiB, four operations),
against this package's:

| arm                | rows | match | differ |
| ------------------ | ---: | ----: | -----: |
| glibc iconv        |  352 |   352 |      0 |
| GNU libiconv (850) |  176 |   176 |      0 |
| Go x/text (UTF-8)  |  176 |   176 |      0 |
| ICU 78.3           |  352 |   328 |     24 |

GNU libiconv has no IBM437, and x/text no UTF-16 operations. ICU differs
on the `invalid` rows of 256 bytes and up, the only inputs with bytes
0x1A, 0x1C, and 0x7F: ICU's `ibm-437` and `ibm-850` (IBM's own tables,
not Microsoft's) rotate them, 0x1A to U+001C, 0x1C to U+007F, and 0x7F to
U+001A (`printf '\x1a\x1c\x7f' | uconv -f ibm-437 -t utf-8` gives
`1c 7f 1a`). Unicode's tables, glibc, libiconv, and x/text map them to
themselves, as this package does.

The standard's machinery around them: they are not in the standard, so
they have no labels and `Encoding.forLabel` never returns them (not for
`ibm437`, `cp437`, or `437`; the standard's label table is the whole label
set, and the oracle checks that `forLabel` agrees with encoding_rs on
those). `name()` is `IBM437` and `IBM850`, `outputEncoding()` is the
encoding itself, and a byte order mark with `.sniff` switches to UTF-8 or
UTF-16 as it does for any label. Decoding and encoding are the standard's
single-byte decoder and encoder over these tables: a code point outside a
table is a numeric character reference in html mode and `unmappable` in
fatal mode.

## 7. Decoding without optionals: the tables' `decode` as a `u32`, and `tryPut`

Two requests from the Korean orb (korean-20261102.md), both about a
`?u21` or `?usize` that LLVM carries through a stack slot on every
character once it is inlined in a decode loop.

**The tables' `decode` returns a `u32`, 0 for none, instead of `?u21`.**
Every layout (`flat`, `japanese_paged`, `chinese_rank`) emits `pub fn
decode(pointer: u32) u32`, and the callers in japanese.zig, gb18030.zig,
big5.zig, and euc_kr.zig test `cp != 0`. No index maps a pointer to
U+0000, so 0 is free. `test/layout_check.zig` checks every pointer against
the index as before, now against 0 rather than null; `zig build gen-check`
and `zig build test-layouts` pass on all 27 index and layout pairs.

**A `tryPut` that returns 0 when the code point does not fit**, in place of
`?usize`, in the two-byte fast paths of gb18030 and Big5 and in
ISO-2022-JP's two-byte run. Measured both alone and on top of the `u32`
decode, it changes nothing: +0.5% geomean alone (`put`), −0.1% on top of

committed. euc_kr.zig keeps its private writer, `putIndex`, which already
returns 0 for no room: replacing it with the general writer (one that
